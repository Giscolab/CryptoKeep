Résumé exécutif

Verdict : Vault Personal n'est pas prêt pour la production pour stocker de vraies identifiants. La base de code actuelle est un prototype de navigateur utile avec chiffrement WebCrypto, mais le dépôt et les affirmations du produit surestiment considérablement le modèle de sécurité mis en œuvre.

Fait issu du code/documents. L'application active utilise AES-GCM du WebCrypto du navigateur avec PBKDF2-HMAC-SHA512 et IndexedDB. Elle conserve également les entrées déchiffrées dans un coffre JavaScript en mémoire, affiche les mots de passe dans les valeurs d'entrée du DOM, écrit une sauvegarde du coffre encodée dans le localStorage, expédie des fichiers crypto/stockage hérités dupliqués, et annonce des fonctionnalités qui sont absentes ou inactives.

Estimation technique. Le risque le plus important n'est pas une mauvaise utilisation immédiate d'AES-GCM. Le risque plus important est le décalage de confiance : la documentation, l'interface et la communication du README impliquent un produit de sécurité industriel, isolé et à connaissance nulle, tandis que les preuves de mise en œuvre montrent un prototype local monopage avec un confinement à l'exécution incomplet, une vérification limitée et une sémantique de stockage fragile.

10 constatations critiques principales

1. L'affirmation de force du KDF dans le README est fausse

critique

Fait. README.md:40 affirme 600 000 itérations PBKDF2. Le code actif code en dur 150 000 à trois endroits.

README.md:40
PBKDF2-HMAC-SHA512 | 600 000 itérations

scripts/core/crypto/pbkdf2.js:23
iterations: 150000,

scripts/core/storage/schema.js:13
iterations: 150000,

Cela surestime matériellement la résistance à la force brute hors ligne. Le nombre d'itérations n'est pas non plus appliqué à partir des métadonnées de version du coffre lors de la dérivation.

2. Le coffre déchiffré reste résident après le déverrouillage et après le verrouillage automatique

critique

Fait. L'application déchiffre chaque entrée dans this.vault. Le verrouillage automatique ne met à zéro que masterKey et efface le champ du mot de passe.

scripts/core/vault/manager.js:119-124
const data = await decryptData(entry, this.masterKey);
decrypted.push({ id: entry.id, ...data });
this.vault.clear();
decrypted.forEach(entry => this.vault.addEntry(entry));

scripts/app.js:226
vaultManager.masterKey = null;

L'écran de verrouillage ne prouve pas que le texte en clair est parti. Une extension de navigateur, un script injecté, un accès à la console, ou un état post-XSS peuvent toujours atteindre les entrées précédemment déchiffrées via le graphe d'objets de l'application.

3. Les mots de passe sont rendus dans les valeurs du DOM

critique

Fait. La liste du coffre place les mots de passe en texte clair dans les chaînes de modèle HTML et les valeurs d'entrée.

scripts/ui/vault-list/vault-list.js:153
wrapper.innerHTML = `...`

scripts/ui/vault-list/vault-list.js:196
navigator.clipboard.writeText(input.value)

La ligne d'entrée exacte se trouve à l'intérieur de ce modèle : <input type="password" value="${entry.password}" ...>. Le masquage du type de champ est uniquement visuel ; le secret est toujours dans le DOM.

4. La sauvegarde localStorage crée une deuxième surface de persistance du coffre

critique

Fait. Chaque sauvegarde écrit une copie encodée en base64 du coffre chiffré dans le localStorage.

scripts/core/storage/manager.js:47
// sauvegarde également dans localStorage

scripts/core/storage/manager.js:104
localStorage.setItem('vaultBackup', encoded);

La base64 n'est pas une protection. Le localStorage est lisible par les scripts et persistant, élargissant le rayon d'action de toute attaque XSS, compromission d'extension ou vol de profil de navigateur.

5. Le chemin de mise à jour du stockage efface le coffre avant d'écrire les données de remplacement

critique

Fait. Les chemins de sauvegarde et d'importation effacent le magasin avant de placer le nouvel enregistrement unique du coffre.

scripts/core/storage/manager.js:41-44
await store.clear();
await store.put({
  id: 'current',
  entries,
  meta
});

Le code n'attend pas la fin de la transaction et n'utilise pas de schéma de validation intermédiaire/retour en arrière. Une défaillance en cours d'opération peut détruire la seule copie IndexedDB avant que le remplacement ne soit durable.

6. Les affirmations de protection par Web Worker et Spectre ne sont pas étayées

critique

Fait. Le README affirme l'isolation par Web Worker et la protection contre Spectre. L'application active importe des assistants de worker mais utilise deriveMasterKey, et non deriveMasterKeyWithWorker. Les chemins des workers sont également incorrects pour le chemin de document actuel.

README.md:41
Web Workers | Protection contre les attaques Spectre

scripts/app.js:257
const key = await deriveMasterKey(password, salt);

scripts/core/crypto/pbkdf2.js:37
new Worker('./core/crypto/workers/pbkdf2.worker.js', { type: 'module' });

Depuis index.html, cette URL de worker se résout en dehors de /scripts/. Même si corrigée, les Web Workers ne fournissent pas de protection contre Spectre pour les secrets dans un onglet de navigateur.

7. La CSP n'est pas stricte et contredit le module de sécurité

critique

Fait. La CSP HTML expédiée autorise les scripts/styles de CDN externes et les styles unsafe-inline. Le module CSP dynamique plus strict n'est injecté que dans un environnement de développement de type Node, qui n'est pas l'environnement de navigateur d'exécution pour cette application statique.

index.html:11-12
script-src 'self' https://cdnjs.cloudflare.com ;
style-src 'self' 'unsafe-inline' https://cdnjs.cloudflare.com ;

scripts/security/csp.js:25
"style-src 'self'", // suppression de unsafe-inline

La politique active est plus faible que la politique revendiquée. Font Awesome est chargé depuis cdnjs sans SRI.

8. La documentation annonce une architecture de sécurité inexistante

critique

Fait. Le README fait référence à des dossiers et fichiers qui ne sont pas dans le dépôt : core/crypto-engine.js, ui/biometric-auth/, workers/db.worker.js, et SECURITY.md.

README.md:117

README.md:122
db.worker.js           # Accès IndexedDB

README.md:168

Ce n'est pas cosmétique. Pour un gestionnaire de mots de passe, les revendications d'architecture de sécurité non étayées affectent directement les décisions de risque des utilisateurs.

9. La couverture de tests est bien en deçà des standards de coffre à secrets et n'a pas pu être exécutée ici

critique

Résultat de commande. npm test, npm run test:security, et npm run lint ont quitté avec le code 1 dans ce shell. L'exécution directe des tests Node s'est interrompue avec Assertion failed: ncrypto::CSPRNG(nullptr, 0).

package.json:8-9
"test": "node tests/vault.spec.js && node tests/crypto.spec.js && node tests/vault-filters.spec.js",
"test:security": "node tests/security-no-plaintext.spec.js"

Examen statique des tests. Les tests existants couvrent le crypto aller-retour de base, les opérations de collection, les filtres, et une régression. Ils ne couvrent pas le texte chiffré altéré, le comportement de verrouillage par mot de passe erroné, la corruption du stockage, le retour en arrière d'importation, la purge de texte clair par verrouillage automatique, la CSP, l'expiration du presse-papiers, ou les échecs de migration.

10. Les indicateurs de confiance de l'interface sont codés en dur avant que l'état d'audit réel n'existe

critique

Fait. Le tableau de bord affiche des mesures de sécurité visibles temporaires dans index.html, y compris le score et les comptages, avant que le coffre ne soit déverrouillé et mesuré.

index.html:288-303

Cela présente de la confiance avant les preuves. Le JavaScript ultérieur met à jour certaines valeurs, mais l'expérience utilisateur initiale commercialise toujours un score de sécurité qui n'est pas lié à une posture de sécurité de produit vérifiée.

A2 Audit de l'implémentation cryptographique

Fait. L'application utilise PBKDF2 du WebCrypto avec SHA-512, dérive une clé AES-GCM 256 bits non extractible, et chiffre les charges utiles JSON avec des IV aléatoires de 96 bits.

scripts/core/crypto/aes-gcm.js:11
const iv = crypto.getRandomValues(new Uint8Array(12));

scripts/core/crypto/pbkdf2.js:21-28
name: 'PBKDF2',
salt: salt,
iterations: 150000,
hash: 'SHA-512'

Le bon choix de primitive ne compense pas l'absence de politique cryptographique

élevée

Il n'y a pas d'objet de politique cryptographique centralisé, pas de calibrage du KDF, pas d'application de version crypto par coffre lors de la dérivation, pas de chemin de mise à niveau pour l'augmentation du travail du KDF, et pas d'authentification de métadonnées indépendante au-delà de l'authentification de charge utile AES-GCM.

L'acceptation du mot de passe maître est bien trop faible

élevée

Fait. scripts/app.js ne rejette que les mots de passe vides et les mots de passe de moins de 6 caractères. Il n'y a pas de seuil d'entropie pour le mot de passe maître.

scripts/app.js:250-253
if (!password || password.length < 6) {
  showToast("The master password must contain at least 6 characters.", "error");
  return;
}

La génération d'IV est correcte, mais l'unicité n'est pas surveillée

moyenne

L'IV aléatoire de 12 octets est approprié pour AES-GCM. Cependant, l'application stocke un index iv avec unique: false et n'impose pas ni ne teste la gestion des collisions. La probabilité de collision aléatoire est faible, mais un gestionnaire de mots de passe devrait toujours avoir des tests de régression sur l'unicité de l'IV et la défaillance d'altération.

Limite. Le WebCrypto du navigateur ne peut pas protéger contre les scripts malveillants s'exécutant dans la même origine, les extensions de navigateur, les appareils compromis, les lecteurs de presse-papiers, ou le grattage DOM post-déverrouillage. La documentation ne communique pas honnêtement cette limite.

A3 Audit de robustesse du stockage et de la persistance

Fait. IndexedDB utilise une base de données, un magasin d'objets et un enregistrement unique de coffre actuel.

scripts/core/storage/indexeddb.js:8
const request = indexedDB.open('VaultDB', 1);

scripts/core/storage/indexeddb.js:14
db.createObjectStore('vault', { keyPath: 'id' });

Le stockage est fonctionnel, pas industriel

critique

Le modèle stocke un coffre entier comme un enregistrement de type blob. L'isolation des entrées est uniquement logique dans le tableau. Il n'y a pas de journal d'ajout, pas de validation en deux phases, pas d'anneau de versions de sauvegarde, pas d'enveloppe de somme de contrôle, pas de récupération de dernière version connue, et pas de registre de migration.

Le format d'importation/exportation n'est pas prêt pour la migration

élevée

Fait. L'exportation est du JSON brut ; l'importation vérifie l'extension et analyse le JSON. L'importation de l'application vérifie uniquement meta.salt et meta.validation.

scripts/core/storage/backup.js:7-9
const json = JSON.stringify(vaultData);
const blob = new Blob([json], { type: 'application/json' });

scripts/app.js:363
if (!data.meta || !data.meta.salt || !data.meta.validation) { ... }

Il n'y a pas de magie de format, de signature de schéma, d'application de version de politique crypto, ou de validation pré-écrasement par déchiffrement avec la clé actuelle/fournie.

Le chemin d'importation CSV semble cassé et non sûr

élevée

Fait. scripts/utils/import-csv.js fait référence à showToast, vaultManager, et renderVaultEntries sans les importer. Il analyse également le CSV par split(','), qui casse les virgules entre guillemets.

scripts/utils/import-csv.js:55-63
await vaultManager.addEntry(entry);
const updated = await vaultManager.decryptAllEntries();
renderVaultEntries(updated);

A4 Audit de la sécurité à l'exécution

Fait. Les contrôles à l'exécution incluent le verrouillage automatique, un assistant de mise à zéro mémoire, des métadonnées CSP, une copie presse-papiers, et du code de vérification de violation HIBP. La profondeur d'application est bien plus faible que ce que l'interface et le README impliquent.

Le verrouillage automatique est un verrou d'écran, pas une purge de texte clair

critique

Le verrouillage automatique efface la référence de clé dérivée et le champ du mot de passe maître, mais il n'efface pas this.vault.entries, les valeurs de mot de passe DOM déjà rendues, l'état d'accès récent, ou le contenu du presse-papiers.

L'effacement du presse-papiers est annoncé mais non mis en œuvre

élevée

Fait. Des écritures presse-papiers existent dans scripts/utils/clipboard.js:13, scripts/ui/dashboard.js:51, et scripts/ui/vault-list/vault-list.js:196. Aucun effacement basé sur délai n'a été trouvé. index.html:597 décrit un effacement automatique du presse-papiers après 60 secondes.

La console et la journalisation de l'interface peuvent exposer des objets sensibles à la sécurité

élevée

Fait. StorageManager.saveVault journalise les entrées et les métadonnées. setupUILogger reflète la sortie de la console dans la page.

scripts/core/storage/manager.js:39
console.log('[Vault DEBUG] Data to save:', entries, meta);

scripts/utils/logger.js:18-21
console[method] = function (...args) {
  write(method.toUpperCase(), args);
  original.apply(console, args);
};

Les entrées chiffrées ne sont pas en texte clair, mais les métadonnées et les traces opérationnelles n'ont pas leur place dans la journalisation de l'interface de production.

Le code HIBP contredit la messagerie absolue « pas d'internet » si activé

moyenne

Fait. scripts/security/hibp-service.js:60 appelle https://api.pwnedpasswords.com/range/. L'application définit window.__VAULT_HIBP_ENABLED__ = false, donc c'est désactivé par défaut, mais la capacité existe et devrait être explicitement divulguée.

A7 Analyse de la confiance du frontal et de l'expérience utilisateur

Fait. L'application présente des cartes de score de sécurité, des mesures, des zones critiques, des vues de rapport de sécurité, des panneaux d'audit, de nombreux thèmes, et un langage de tableau de bord soigné. Plusieurs contrôles sont temporaires ou non reliés à des garanties de sécurité solides.

Le soin de l'interface masque des contrôles de sécurité incomplets

élevée

Le gestionnaire de mots de passe a une surface riche, mais les modes de défaillance principaux ne sont pas gérés au même niveau : coffre corrompu, sauvegarde interrompue, importation de format incompatible, faiblesse du mot de passe maître, état de verrouillage, effacement du presse-papiers, et confinement XSS.

Les flux de sauvegarde et de restauration ne sont pas sûrs pour les utilisateurs non experts

élevée

L'importation écrase le coffre actuel après une confirmation générique. Elle ne valide pas par déchiffrement le coffre importé avant remplacement, ne conserve pas de point de restauration visible de dernière version connue, et demande à l'utilisateur de recharger après l'importation.

L'interface de compte/persona sape la clarté de la confiance local-only

moyenne

La barre latérale inclut des valeurs d'identité temporaires telles que « John Doe » et un langage de suppression de compte, alors que le produit est local-only et n'a pas de véritable backend de compte. Cela peut confondre les utilisateurs sur ce qui existe et ce qui est protégé.

A8 Verdict de préparation pour la production industrielle

Verdict final : Ne stockez pas de vraies identifiants dans cette application aujourd'hui. Elle devrait être traitée comme un prototype éducatif/local jusqu'à ce que le stockage, la sécurité à l'exécution, la documentation et le modèle de vérification soient reconstruits.

Fait. Le code démontre une preuve de concept WebCrypto locale plausible. Estimation. Il est approximativement à 20 à 25 pour cent du chemin vers un gestionnaire de mots de passe local industriel, en supposant que la cible souhaitée est un coffre de navigateur autonome digne de confiance.

Feuille de route de reconstruction priorisée

  1. Réécrire la promesse de sécurité. Supprimer « militaire », « protection contre Spectre », les garanties de Web Worker non étayées, les comptages de KDF faux, les références de fichiers inexistants, et les affirmations absolues de contexte de navigateur.
  2. Centraliser la politique crypto. Ajouter une configuration crypto versionnée unique, appliquer les paramètres du KDF pilotés par métadonnées, élever/calibrer le travail du KDF, et construire un chemin de migration.
  3. Reconstruire la sémantique de verrouillage. Lors du verrouillage, purger l'état du coffre déchiffré, effacer les valeurs de mot de passe rendues, effacer les champs d'édition, annuler les minuteries, et tenter l'écrasement du presse-papiers avec une messagerie honnête des limites du navigateur.
